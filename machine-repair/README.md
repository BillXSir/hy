# machine-repair

现场设备（机器人 / 边缘盒子）的**维修操作手册 + 可执行脚本**。每个问题一个目录，内含说明、脚本、真实案例。

面向的场景是"设备已经在客户现场或实验室跑着，人不在旁边或只有一个 SSH"，所以所有操作都按**可远程、可回滚、不依赖现场干预**来设计。

## 铁律

> **先跑安全模式拿到判定，再分析。**

任何新问题都先执行一条**只读或可逆**的命令，把模糊的"现象"收敛成一个明确的 verdict，再决定要不要动系统。

反面教材：看到"蓝牙搜不到"就去换天线、重装系统、刷固件。这类问题里绝大多数是**软件状态**问题，硬件坏的概率很低。

安全模式的三条硬约束：

1. **不写文件**（除显式 `--install`）
2. **不重启**
3. **不碰固件 / 内核配置**；固件缺失时只报告，不猜测、不下载

## 问题索引

| 目录 | 症状指纹 | 一键操作 |
|---|---|---|
| `bluetooth-dead-hci0/` | `hciconfig` 有 `hci0`，但 `DOWN` + `BD Address: 00:00:00:00:00:00` + `Features` 全零 | `sudo ./bluetooth-dead-hci0/bt-dead-hci0.sh` |

多台设备可以连带远程流程一起跑（`deploy-remote.sh` 默认目标 `YARBO@37.38.39.8`，不带参数即可）：

```bash
machine-repair/bluetooth-dead-hci0/deploy-remote.sh --install --reboot
```

## 目录约定

```
machine-repair/
└── <问题名>/
    ├── README.md          现象 → 判定指纹 → 一键操作 → 根因 → 修复 → 验证 → 回滚
    ├── <问题名>.sh        可执行脚本，默认安全模式
    └── case-*.md          真实案例的证据链与踩过的坑
```

约定：

- **每个脚本都必须自己能判定**，不能要求人先手工跑一堆诊断命令再喂给它
- **默认模式必须可逆**；破坏性或持久化动作一律藏在显式参数后面（`--install` / `--force`）
- **持久化改动前自动备份**，并提供对称的 `--uninstall`
- 案例里保留**失败假设**（当时以为是什么、实际是什么），这是下次少走弯路的唯一办法

## 新增一个问题的模板

1. 建目录 `<问题名>/`，写 `README.md`，第一节就是**症状指纹**（一行能判真伪的那种）
2. 写脚本，默认模式只读或可逆
3. 在设备上实测：**正常态**跑一遍（应 no-op）、**故障态**跑一遍（应修复）
4. 至少做一次**重启验证**，确认持久化方案在真实开机序列里生效
5. 把证据链与失败假设写进 `case-*.md`
6. 回到本 README 的"问题索引"加一行

## 脱敏

设备**有线/内网静态 IP 可以写进脚本**（例：`DEFAULT_TARGET="YARBO@37.38.39.8"`），省掉每次输参数 —— 这是唯一的例外。

以下一律不进仓库：登录凭据 / 密码 / 密钥、设备序列号、完整 MAC、客户名与现场地址。
脚本里不得出现任何密码；需要凭据时由执行者交互输入。
